## 2. 范围（In Scope）

EVCS Manager 作为“充电站运营管理平台”，覆盖以下核心能力：

- **身份与租户**：用户登录、鉴权、RBAC；多租户隔离与租户配置
- **站点与设备管理**：站点基础信息维护；设备接入、状态与基础档案
- **订单与计费**：计费方案配置；订单创建、状态流转、结算数据记录
- **支付与对账（能力边界内）**：支付订单记录；支付回调处理、幂等与状态落库
- **协议与事件流**：协议事件接入；关键事件通过 MQ 广播并被下游消费以驱动状态同步
- **运维支撑**：健康检查、日志、指标与监控基础接入

## 3. 非范围（Out of Scope）

以下内容不在本文件的强制范围内（可能在后续迭代或归档中出现）：

- 资金清结算全链路、财务报表体系（本期只要求支付记录与回调落库的正确性）
- 智能调度/电网侧优化、负荷预测等算法能力
- 设备固件升级平台、设备全量远程运维平台（本期聚焦“接入与事件闭环”）

## 4. 角色与主要使用者

- 平台管理员：租户/用户/权限配置、平台参数维护
- 运营人员：站点与设备管理、订单查询、异常处理
- 第三方系统：通过 API 或 MQ 对接事件、订单、支付等能力
- 设备侧/协议侧：上报事件与状态（WebSocket/HTTP 等），驱动平台状态同步

## 6. 关键业务流程（摘要）

### 6.1 登录与多租户上下文

- 请求必须携带并解析租户上下文（如租户标识、用户身份）。
- 异步/消息消费场景必须显式传播租户上下文，禁止出现“跨租户写入”。

#### 6.1.1 多层级租户模型

EVCS 的多租户不仅是“租户隔离”，还需要支持**租户的分级管理**（典型场景：集团/区域/子公司/运营主体）。本项目对“多层级租户”的需求口径定义如下：

- **平台层（L0）**：平台/运营方视角，具备全局治理能力（创建/禁用租户、配置配额与策略、审计）。
- **组织租户（L1）**：业务主体（集团/公司/运营商），拥有自己的用户、角色、站点与业务数据。
- **子租户（L2+）**：隶属于某个上级租户的下级组织单元（如区域公司、项目公司）。

说明：层级深度不做硬限制，但必须保证“向下可管、向上不可越权”。层级能力以权限与数据隔离规则约束，而不是仅靠 UI。

#### 6.1.2 分级管理规则（强制）

- **租户隶属关系**：每个非平台租户必须且仅能隶属于一个上级租户（树结构）；上级可管理其所有下级（含后代），下级不得管理上级。
- **租户生命周期与状态**：禁用上级租户时，其下级租户应同步不可用（至少鉴权层面拒绝请求）；恢复上级租户时下级是否自动恢复需有明确策略（默认不自动恢复，避免误开）。
- **配额与能力开关**：平台层可配置租户配额/能力开关（如最大站点数/设备数/并发会话数/协议类型）；上级租户可在平台授权范围内为下级分配“子配额”，总和不得超过自身配额。
- **角色与权限继承**：平台层可定义基础模板；权限允许“继承 + 收敛”，下级不得超过上级授权上限；上级管理员可管理下级用户，但默认不直接操作下级业务数据（除非显式授权与审计）。
- **审计与可追踪性**：跨层级管理行为（创建子租户、重置子租户管理员、变更配额/开关等）必须具备审计日志与责任人。

#### 6.1.3 数据隔离与跨层访问规则（强制）

- **默认隔离**：业务数据（站点/设备/订单/支付等）默认严格按 `tenant_id` 隔离。
- **上级租户查看下级数据（可选能力，需显式开关）**：仅允许“只读/统计类”跨层查询，必须显式声明范围（如 `tenantScope=SELF_AND_DESCENDANTS`）；跨层写操作默认禁止，如确有需求必须通过专用管理接口、强鉴权与审计实现。
- **平台层访问**：平台层可访问全局数据，但必须强制审计与最小权限原则（按功能授予，不授予“万能管理员”）。
- **异步与消息场景**：消息体必须携带 `tenant_id`（必要时含层级信息），消费者必须基于该租户上下文落库；禁止出现“消费端根据自身租户写入”的隐式行为。

#### 6.1.4 接口与权限约定（更落地的实现口径）

本节定义“多层级租户分级治理”在接口与鉴权层的**需求约束与验收口径**。

具体的权限点命名、API 参数命名、审计动作枚举等实现细节，统一下沉到设计文档以避免需求侧漂移：

- 设计落地约定：[docs/architecture/TECHNICAL-DESIGN.md](TECHNICAL-DESIGN.md)

##### A) 权限与越权约束（需求层）

- 下级租户不得拥有任何“向上管理/向上访问”的能力（无论角色名称如何）。
- 上级租户跨层访问下级数据必须满足：显式声明范围 + 专门授权 + 强制审计。
- 跨层写入默认禁止；若确需开放，必须通过“专用管理接口”落地，并具备强鉴权、显式目标租户与完整审计。

##### B) 接口语义（需求层）

1. **租户管理接口（L0/L1 管理能力）**
   - 语义：创建子租户、禁用/恢复子租户、调整配额/能力开关、指定/重置子租户管理员。
   - 约束：只能对“本租户的后代租户”生效；不得对上级/兄弟租户生效。
2. **业务查询接口（站点/设备/订单/支付等）**
   - 默认：仅返回“当前租户”的数据。
   - 若支持跨层只读：必须通过“显式参数/字段”开启范围（参数名由设计统一约定），并在鉴权层校验跨层只读权限。
3. **业务写接口（创建/更新/删除）**
   - 默认：只允许写入当前租户的数据。
   - 跨层写入：默认禁止；若确需开放，按“专用管理接口”治理。

##### C) 审计（需求层）

只要发生以下任一情况，必须写审计日志：

- 跨层管理行为（创建/禁用/恢复子租户、重置子租户管理员、调整配额/能力开关）。
- 跨层只读访问（显式开启“包含后代/下级”范围）。
- 跨层写入（如被特批开放）。

审计日志必须至少包含以下信息（字段名由设计统一约定）：

- 操作者所属租户与操作者身份
- 目标租户
- 动作类型
- 请求追踪标识（如 requestId/traceId）
- 结果（成功/失败、必要时含错误码/失败原因）
- 操作时间
- 关键变更差异（脱敏后）

##### D) 测试用例基线（验收可直接执行）

- **默认隔离**：同一接口在“范围开关关闭/默认范围”时只能看到本租户数据。
- **跨层只读**：具备“跨层只读权限”的上级租户，开启“包含后代/下级范围”后可读到后代租户数据；无该权限时必须拒绝。
- **向上越权拒绝**：下级租户不得读取/管理上级租户；任何尝试应返回明确错误（403/业务错误码）。
- **生命周期联动**：禁用上级租户后，下级租户请求应不可用（至少鉴权层拒绝）；恢复策略按需求口径执行。
- **审计必达**：跨层只读/管理行为必产生审计记录，且包含最小字段集合。
- **异步传播**：消息消费/异步任务中租户上下文正确，消费端不会写入错误租户。

多租户与异步上下文约束见 RFC：

- [docs/architecture/TENANT-CONTEXT-ASYNC-RFC.md](TENANT-CONTEXT-ASYNC-RFC.md)

### 6.2 协议事件闭环（设备 → MQ → 状态落库）

- 协议侧接收到事件后，必须发布可消费的事件消息（包含关键定位字段，例如 `stationId`、会话标识等）。
- 下游服务消费事件后应完成：站点/设备状态更新、订单状态更新、必要的补偿与幂等。

### 6.3 订单与支付闭环（摘要）

- 订单状态机必须清晰、可追踪（至少支持：创建、充电中、结束/完成、失败/取消）。
- 支付回调必须幂等；重复回调不得导致重复入账或状态回退。

## 7. 非功能性需求（NFR）

### 7.1 可用性与可靠性

- 关键链路（协议事件、订单状态流转、支付回调）必须具备幂等与可重试策略。
- 消息处理需支持死信/告警或可观测的失败追踪。

### 7.2 性能与容量（基线）

- 列表查询必须分页；禁止无界全表扫描。
- 热点查询应有可解释的索引策略与缓存策略。

### 7.3 安全

- 强制鉴权；敏感配置（密钥、连接串）禁止硬编码。
- 日志不得在 INFO 输出敏感信息。

### 7.4 可观测性

- 关键操作应具备结构化日志字段（至少含租户、请求 ID、业务主键）。
- 服务需提供健康检查端点并接入监控。

## 8. 数据与一致性约束（摘要）

- 数据库设计与字段基线见：[docs/development/DATABASE-DESIGN-STANDARDS.md](../development/DATABASE-DESIGN-STANDARDS.md)
- 租户字段 `tenant_id` 必须参与隔离与索引策略；软删除字段遵循项目约定。

## 9. 验收清单（最小可执行）

- 架构/分层符合 SSOT 要求（Controller → Service → Domain/Repository），禁止跨服务直连数据。
- 多租户隔离：任意接口/消费逻辑不得跨租户读写；异步上下文可追踪。
- 多层级租户：上级可管下级（生命周期/配额/用户管理），下级不可越权；跨层访问遵循“显式声明 + 只读优先 + 审计”。
- 协议事件闭环：关键事件可通过 MQ 到达下游并正确落库（站点/订单状态一致）。
- 支付回调：幂等、可重试，状态机不回退。
- 质量门禁：单元测试与必要的集成测试通过；覆盖率阈值以团队约定/CI 为准。
